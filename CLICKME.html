04 · Write-up

The use case and the value it provides

Support and pre-sales teams handle incoming client tickets in Trello. They work in blocks: a pile in the morning, another in the afternoon, focus work and meetings in between.

I built a Dust agent that fits that rhythm.

The agent performs the following actions twice a day (trigger):

  • reads the Inbox, including screenshots attached to tickets
  • sets priority and category on the board
  • searches the product documentation
  • gives me a report with a draft reply per ticket

I, as a member of the support team, review the report in Dust and reply in plain language: approve, correct, or take a ticket myself. The agent posts the approved replies as comments in Trello, under my name with a "via Dust" signature, and moves the cards.

The value is time and attention.

  • Tickets that can be answered via the docs would take one approval instead of ten minutes of reading and searching.
  • Complex tickets get the agent's analysis as a starting point. I, as a support staff, can open a dedicated chat for any of the ongoing complex tickets with the possibility to load only the ticket I'm interested in and with access to the company's docs.
  • Nobody switches apps. Analysis and decisions happen in Dust; the record stays in Trello.

This also makes Dust sticky.

The agent runs on a schedule to triage and analyze the tickets, but I can also ask it for the Inbox (or one specific ticket) at any moment.

How the solution works

A custom MCP server, generated with Claude Code from a plan I wrote after a 1-h brainstorm (multiple chat threads and lookups). About 350 lines of TypeScript, three dependencies: the MCP SDK, express, zod.

It exposes seven tools:

  1. list_cards: the cards of one list, compact
  2. get_card: one card with its comments and attachment list
  3. get_attachment: download an image so the agent can look at it
  4. set_custom_field: priority, category, customer, by name and human value
  5. add_comment: analysis, drafts, approved replies
  6. move_card: advance the card to the next list
  7. archive_stale_cards: bulk cleanup with a dry-run preview

Three design choices that matter:

  • Outputs are shaped for the model: a card is a dozen readable fields, not sixty with ids.
  • Guardrails are in the code, not the prompt: dry run by default, no delete tool at all.
  • The scheduled run reads and classifies but posts nothing. Every comment in Trello follows a human decision.

Dust connects to the server as a remote MCP tool. The server connects to Trello with an API key and token. Dust also has the product documentation as a Google Drive data source, so one agent reads both the board and the docs.

The server is stateless: every request carries what it needs, and the board itself is the state. A processed card leaves the Inbox, so the afternoon run only sees what is new. Nothing to store, nothing to sync, and a human can drag a card back to force a re-run.

It ships as a Docker image.

The POC makes two deliberate simplifications:

  1. One board per deployment, set by an environment variable.
  2. One shared credential: a bearer token between Dust and the server, one Trello token behind it.

Production removes both. The server code stays the same.

Same image, on the customer's infrastructure, so credentials never leave their perimeter. Two things are added next to it: a small auth service and an encrypted token store.

There are two identities to handle, and they stay separate.

1. Who the employee is (Dust to MCP server)

Dust connects to the auth service through OAuth, with credentials set to Personal, so each user authorises once. The auth service checks identity in one of two ways:

  • A. Its own user list. Fine for a small company.
  • B. Delegation to the customer's IdP through OIDC (OpenID Connect: a thin layer on top of OAuth that adds identity). The user sees their usual SSO screen. This is the large-company path.

Same code, different identity provider behind it.

2. Who the employee is in Trello (MCP server to Trello)

The first time a user calls a tool via MCP, the server sends them once to Trello's own OAuth 2.0 consent screen. The returned token is stored encrypted, keyed by the identity from step 1. If the company runs Trello under Atlassian SSO, that consent screen logs in through the IdP automatically.

Result: every action in Trello appears under the real person's name, and the user's own Trello permissions bound what the agent can see. This means we get least privilege for free.

Scaling, three axes

  • Replicas scale with traffic: the server is stateless, so any number of copies sit behind a load balancer.
  • Tokens scale with users: Trello's rate limit is per token, so more users means more capacity, not less.
  • Deployments scale with security boundaries: one image per zone if a company needs isolation.

The storage needs remain limited and can be handled with the customer's database solution.

Production hardening, small items: a five-minute TTL on the board-metadata cache, one log line per tool call, an IP allowlist for Dust's egress.

07 · Write-up

How I tested it

I built the MCP server and hosted it in Railway (Docker container) then connected it to Dust and built the triage agent inside dust. It was very fun.

  • End to end in Dust: morning report, then the correction script, then the stale preview. Reset, re-run.
  • I also had Claude Code test the code locally with the MCP Inspector: all seven tools called against a real board.
  • Negative tests: wrong bearer returns 401; unknown list name returns an error listing the real lists; invalid custom-field option returns the valid options; days below 3 rejected by validation.
  • On Railway: health check, and a 401 from a bare curl on /mcp.

One assumption broke on contact with the API: the seed tried to enable Custom Fields as a Power-Up, which no longer exists as one. Fixed by creating the fields directly.

Details in TESTING.md.

08 · Write-up

Assumptions, tradeoffs, limitations

What I took for granted, what I gave up on purpose, and where the prototype stops.

Assumptions

  • Support teams work in blocks, so twice-daily runs beat real time.
  • The docs are the only source of truth for pricing and policy (weak assumption because in large companies the source of truth is scattered).
  • One Trello board maps to one team (need to add a board id per tool call to make this work with a customer).
  • Every customer-facing reply gets a human approval.

Tradeoffs

  • Custom MCP over the official one: more work, but we get comments, fields and screenshots.
  • Scheduled runs over a webhook: no real time, no second service to host.
  • Bearer over OAuth for the POC: no per-user identity, fifteen minutes instead of a day.
  • One shared Trello token: no attribution, one revocation point.
  • Board as state over a database: nothing to sync, but no run history.
  • Client-hosted over Dust-hosted: the client runs it, the credentials stay home.

Limitations

  • One board per deployment.
  • The list and field cache needs a restart after a rename.
  • Last 20 comments per card.
  • Image attachments only; no upload from Dust to Trello.
  • Everything appears as the token owner in the POC.
09 · Write-up

Why this approach over the alternatives

Five other ways to do this, and what each one gives up.

  1. Official Trello MCP: lacks comments, custom fields, attachments and activity history, which is most of the use case. (Also it's excluded for this assignment)
  2. One shared Dust account for the team: loses attribution in Trello. Tracking and ownership are lost. Users can sign under the CEO's name if they prompt well.
  3. Tagging Dust from Trello comments: moves people back into Trello and needs a webhook receiver. This should be a different feature and implementation having Dust as a member of the team and not a "personal agent."
  4. n8n or Zapier: a runtime and a UI to maintain, more dependencies, and more Auth work with customer deployment.
  5. Data ingestion of the board into Dust: read-only and lags the source. Could complement this later as a searchable archive of resolved tickets. (As I mentioned earlier, knowledge is scattered in large companies).

What I built is the smallest thing that lets people work from Dust while Trello stays the system of record.

And I'll say it again: it was super fun.
